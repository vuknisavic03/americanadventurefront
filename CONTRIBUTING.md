# Contributing

## Working agreement

`main` must remain releasable. Work is delivered through small, reviewable pull requests from short-lived branches.

### Branch naming

- `feat/<scope>` - new product capability
- `fix/<scope>` - defect correction
- `chore/<scope>` - tooling, repository, or maintenance work
- `docs/<scope>` - documentation-only work
- `refactor/<scope>` - behavior-preserving structural improvement
- `test/<scope>` - test coverage or test infrastructure

Use lowercase kebab-case, for example `feat/swt-preapplication`.

### Before starting

1. Confirm the relevant FR, NFR, BR, or web requirement.
2. Update local `main` and branch from its latest verified commit.
3. Confirm or update the requirement status in `docs/requirements/traceability-matrix.md`.
4. Link the change to a GitHub issue unless it is a trivial repository correction.
5. Keep one coherent objective per branch.
6. Record a new ADR before making a material architecture decision.
7. Use the Node.js version from `.nvmrc` and the exact npm version declared in the relevant
   `package.json` `packageManager` field before changing a lockfile.

### Commits

Use Conventional Commits:

- `feat(scope): description`
- `fix(scope): description`
- `chore(scope): description`
- `docs(scope): description`
- `refactor(scope): description`
- `test(scope): description`

Commits should be logically complete, buildable where practical, and free of generated dependencies, secrets, credentials, and real personal data.

### Pull requests

Every pull request must:

- explain the problem and solution;
- reference the applicable requirement identifiers;
- remain focused and reasonably sized;
- include verification steps and relevant test evidence;
- identify database migrations, security impact, personal-data impact, and rollback considerations;
- include screenshots for visible UI changes;
- pass all required automated checks;
- be reviewed before merge.

Use squash merge by default. Delete the feature branch after merge. Do not force-push a shared branch without coordination.

## Definition of Done

A product change is done only when:

- acceptance criteria are implemented and tested;
- authorization and personal-data exposure have been reviewed;
- server-side validation exists for untrusted input;
- state-changing operations are auditable where required;
- background jobs and webhooks are idempotent where applicable;
- database changes include a reviewed migration strategy;
- logs do not expose secrets or sensitive personal data;
- operational and user-facing documentation is updated;
- the pull request passes CI and review.

## Generated files and large assets

Do not commit dependency directories, build output, caches, local environment files, or deployment archives. Large binary assets require an explicit storage decision before being added to Git history.

`apps/platform/next-env.d.ts` is generated by Next.js and can switch between development and
production type paths after `npm run dev` or `npm run build`. Before changing branches, inspect
`git diff -- apps/platform/next-env.d.ts`. If that is the only generated path change, restore the
tracked version or stash it before switching; do not mix it into an unrelated product commit.

Never discard other local changes just to obtain a clean working tree. Preserve them in a named
stash or coordinate with their author first.
